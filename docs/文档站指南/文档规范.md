# 文档规范

一份好的技术文档，应当让读者独立、高效地获取信息，并且在合上文档很久之后，仍记得那个概念到底解决了什么问题。下面是我们对文档的基本要求。

## 讲清根本，而非罗列语法

写一个知识点时，先想清楚它的根本：它到底解决什么问题，它最本质的特点是什么。以 C 语言为例，它的核心是内存——内存如何排布、有什么特点，才是重点，而不是语法本身。抓住了根本，即便日后忘了具体语法，也能凭着对特点的理解，在网上迅速找回细节；只堆砌语法，读者记住的东西转头就忘。

因此，解释一个概念时，优先说明它的来由和本质，再谈具体用法。范围、参数、后缀这类细节可以从本质推导出来，或随手查到，不必占据文档的主干。

## 用平实的文字把事情说清楚

把一件事说清楚，靠的是准确的叙述，而不是不停地分段、分点、加小标题。能用一两段连贯的文字讲明白的，就不要拆成一堆条目。分点和小标题只在真正需要并列或分层时才用，没有必要时，它们只会打断阅读、显得零碎。

语言要平实、克制，像一篇正经的科普，而不是聊天。避免过度使用第二人称，避免口语化的表达和情绪化的修饰。也不要套用"记住一句话""总结起来就是"这类模板式的收尾——该结束的地方自然结束即可。

首次出现的术语或缩写要给出全称，例如"HAL（Hardware Abstraction Layer，硬件抽象层）"。较长的文档用清晰的标题层级组织，方便读者定位。

## 表格与代码用在刀刃上

表格适合承载真正并列、需要横向对比的信息，比如几种模式的差异。不要把本可以用一句话说清的内容硬塞进表格，也不要用大段表格代替叙述——那样看似整齐，实则回避了把道理讲透的责任。

涉及编程的内容应配上简洁、能说明问题的代码示例。示例贵精不贵多，一两个切中要害的例子胜过罗列一堆。

## 实操类文档要能照着做

涉及工具或环境配置的文档，要给出可以逐条执行的步骤，让读者照着做就能完成。常见错误和对应的解决办法可以单独列出，方便遇到问题时快速查找。

## 署名

每份文档末尾都要有署名块，格式如下：

```markdown
> **作者**: [昵称](GitHub链接) | **修改日期**: YYYY-MM-DD
```

如有后续修改者，追加一行：

```markdown
> **作者**: [Qing](https://github.com/ZhangChuqing) | **修改日期**: 2026-07-18
> **修改**: [李四](https://github.com/lisi) | **修改日期**: 2026-08-01 | 补充了 CAN 通信部分
```

署名用 `>` 引用格式，低调而可追溯，方便后来者遇到问题时联系原作者。
