# 内存模型：盒子摆在哪里

上一章说清了指针存的是盒子的地址。可盒子本身又摆在内存的什么位置，它从什么时候开始存在、又在什么时候消失，这些问题指针本身回答不了。这一章把内存这块场地讲透，因为 C 语言的核心正是内存——数据如何在内存里排布、如何分配和释放，比语法本身更值得记住。

## 内存分成三块场地

程序运行时，所有数据都住在内存里，每个变量、每个对象、每个数组都占着其中一段空间。这段空间来自哪里、由谁管理、活多久，取决于它落在哪块区域。C++ 把内存主要分成三块：静态存储区（Static）、栈（Stack）和堆（Heap）。三者的差别归根到底是一件事——盒子的生命周期由谁负责，是编译期就定死，还是随函数进出，还是由程序员手动掌控。

整体的布局大致如下，栈从高地址向下生长，堆从低地址向上生长，中间留出空闲空间供两者伸缩，静态存储区和代码段则在程序加载时就固定下来。

```
高地址
├───────────────
│  栈（Stack）
│  ├── 局部变量
│  └── 函数调用栈帧
├───────────────
│      ↓
│    （空闲）
│      ↑
├───────────────
│  堆（Heap）
│  ├── new/malloc 分配
│  └── 动态增长
├───────────────
│  静态存储区
│  ├── 全局变量 g_counter
│  ├── 静态变量 s_id
│  ├── 字符串字面量 "hello"
│  └── 静态局部变量 foo::callCount
├───────────────
│  代码段（只读）
│  └── 程序指令
低地址
```

## 静态存储区：编译期就定好的盒子

静态存储区的盒子在程序启动时一次性分配好，直到程序结束才释放，生命周期贯穿整个运行期。它的大小在编译期就确定，运行时不再变化，位于独立的数据段，既不占栈也不占堆。全局变量、文件作用域的静态变量、函数内的静态局部变量，以及字符串字面量，都住在这里。

```cpp
int g_counter = 0;               // 全局变量，静态存储区
static int s_id = 100;           // 文件作用域的静态变量，静态存储区

void foo()
{
    static int callCount = 0;    // 函数内的静态局部变量，静态存储区
    callCount++;                 // 值在多次调用之间保持不变
}

const char* msg = "hello";       // 字符串字面量 "hello" 在静态存储区
                                 // 而 msg 这个指针本身在栈上
```

函数内的静态局部变量值得留意：它虽然写在函数里，却不随函数返回而消失，而是在多次调用之间一直保持着上一次的值。

GSRL 这类[嵌入式环境](../嵌入式基础/01-嵌入式系统概述与HAL库.md)对实时性和内存碎片敏感，静态分配在这里有天然优势。它没有运行时开销，布局在编译期已经确定，不需要 `new`/`delete`；它不会因反复分配释放而产生堆碎片；内存用量在编译期就已知，不会在运行时突然不够用。因此 GSRL 中大量的数组和滤波器矩阵，只要能确定最大尺寸，就优先用静态分配。

```cpp
fp32 s_buffer[256];          // 静态分配，编译期确定大小，零运行时开销

fp32* d_buffer = new fp32[size];  // 动态分配，灵活但需要自己管理生命周期
delete[] d_buffer;
```

## 栈：随函数进出自动清理的盒子

栈由编译器自动管理，函数被调用时给它的局部变量分配空间，函数返回时全部自动释放。它速度很快，但空间有限，通常只有几 MB。栈遵循后进先出的规则，像一摞盘子，最后放上去的最先被取走。

```cpp
void foo()
{
    int a = 42;           // 在栈上
    float b = 3.14f;      // 在栈上
    int arr[10];          // 整个数组在栈上
    PIDParam param;       // 结构体在栈上，成员也都在栈上
}  // 函数结束，以上全部自动释放
```

每次函数调用都会在栈顶压入一个新的栈帧（stack frame），里面装着这个函数的局部变量；函数返回时栈帧被弹出，其中的变量随之消失。这套压入弹出的机制正是局部变量"离开作用域就失效"的根本原因，也解释了上一章为什么返回局部变量的地址会得到野指针——盒子随栈帧一起被弹掉了。

```
高地址
├───────────────
│  main 的栈帧
│  ├── int x = 10
│  ├── float y = 3.14
│  └── ...
├───────────────
│  foo 的栈帧      ← 调用 foo() 时压入
│  ├── int a = 42
│  ├── float b = 3.14f
│  └── int arr[10]   (40 字节)
├───────────────      ← foo() 返回后弹出，全部释放
│  main 的栈帧(继续)
│  ...
低地址
```

## 堆：手动申请手动释放的盒子

堆上的内存由程序员用 `new`/`malloc` 手动申请、用 `delete`/`free` 手动释放。它空间大，受系统可用内存限制，但分配和释放都比栈慢，也不遵循后进先出的顺序，任何时候都能分配和释放任意一块。

```cpp
void foo()
{
    int* p = new int(42);        // p 这个指针在栈上，但它指向的 42 在堆上
    fp32* arr = new fp32[100];   // arr 指针在栈上，100 个 fp32 在堆上

    delete p;       // 手动释放
    delete[] arr;   // 数组要用 delete[] 释放
}
```

这里藏着理解 C++ 内存模型的关键：指针变量本身住在栈上，但它指向的数据在堆上，两者分处两块区域。这正是上一章"盒子的地址"落到内存布局上的样子——栈上的小盒子里装着一个门牌号，顺着门牌号找过去，真正的数据在堆里。

```
        栈                         堆
    ┌──────────┐            ┌──────────────┐
    │ p (指针) │──────→     │    42        │  ← int，4 字节
    ├──────────┤            ├──────────────┤
    │ arr(指针)│──────→     │ [0][1]...[99]│  ← fp32[100]，400 字节
    └──────────┘            └──────────────┘
```

堆的麻烦在于释放全靠人记。一旦忘记，栈上的指针随函数返回而消失，堆上的数据却仍占着内存且再也无法访问，这就是内存泄漏。

```cpp
void leak()
{
    int* p = new int[1000];  // 堆上分配 1000 个 int
    // 忘记 delete[] p —— 函数返回后指针 p 消失
    // 但堆上那 1000 个 int 仍占着内存，再也够不到，这就是内存泄漏
}
```

## 三块区域的对比

三者的差别集中在管理方式、速度、大小和生命周期上，横向排开更清楚。

| 特性 | 静态存储区 | 栈（Stack） | 堆（Heap） |
|------|-----------|------------|-----------|
| 管理方式 | 编译器自动 | 编译器自动 | 程序员手动（或智能指针） |
| 分配速度 | 编译期完成 | 极快（移动栈指针） | 较慢（需查找空闲块） |
| 大小限制 | 编译期固定 | 小（通常 1~8 MB） | 大（受系统内存限制） |
| 生命周期 | 程序整个运行期 | 随函数调用/返回 | 手动控制 |
| 碎片问题 | 无 | 无 | 可能出现 |
| 典型用途 | 全局变量、静态变量、字符串字面量 | 局部变量、函数参数 | 动态大小的数据、大对象 |

## 一个对象跨越栈和堆

同一个对象的不同成员可能落在不同区域。下面这个 `SimplePID`，内嵌的成员随对象一起存放，而通过指针在构造时 `new` 出来的数据则另在堆上。

```cpp
class SimplePID
{
    PIDParam m_param;       // 三个 float，直接内嵌在对象里
    fp32* m_errorHistory;   // 一个指针，8 字节，也在对象里
    int m_historySize;      // 一个 int，4 字节
};
```

当这个对象创建在栈上时，`m_param`、`m_errorHistory`、`m_historySize` 都随对象存在栈上，但 `m_errorHistory` 只是个指针，它指向的那段 `fp32[100]` 在堆里。

```
栈
┌──────────────────────┐
│ SimplePID 对象       │
│  ├── m_param         │  ← 内嵌的三个 float，直接存在对象里
│  │   ├── Kp (4字节)  │
│  │   ├── Ki (4字节)  │
│  │   └── Kd (4字节)  │
│  ├── m_errorHistory  │  ← 这是个指针（8字节），存的是地址
│  │       │           │
│  │       ↓           │
│  └── m_historySize   │  ← int，4 字节
└──────────────────────┘
                          ↓
        堆
    ┌──────────────────────┐
    │ fp32[100]            │  ← 构造函数中 new 出来的
    │ [0][0]...[0]         │     400 字节在堆上
    └──────────────────────┘
```

对象本身在栈上，但对象内部通过 `new` 分配的数据在堆上。`m_errorHistory` 只是一个指向真正数据的门牌号，数据本身在别处。

## 移动语义为什么要懂内存

理解了指针在栈、数据在堆这层关系，移动语义就顺理成章。

```cpp
SimplePID pid1(param);                // pid1 在栈上，其 m_errorHistory 指向堆上数组
SimplePID pid2(std::move(pid1));      // 移动构造
```

移动构造做的事情，只是把指针从 `pid1` 复制给 `pid2`，堆上那份数据一个字节都没动。复制完再把 `pid1` 的指针置空，避免两个对象指向同一块内存、析构时重复释放。

```
移动前：                          移动后：
pid1.m_errorHistory → [堆数据]    pid1.m_errorHistory → nullptr
pid2.m_errorHistory → nullptr     pid2.m_errorHistory → [堆数据]（同一个！）
```

不理解指针和堆，就无法理解为什么"复制一个指针"就完成了"移动"——实际上只是换了遥控器，电视机没动。

## 与 GSRL 的关系

GSRL 中堆的使用是受限的（[嵌入式环境](../嵌入式基础/01-嵌入式系统概述与HAL库.md)），但分清三块区域仍然重要。局部变量（如 `KalmanFilter` 实例）在栈上，`std::vector` 内部的数据在堆上，`new` 和 `delete` 在嵌入式环境中要谨慎使用，静态分配则更常见。写移动构造函数、析构函数时，只有清楚每个成员落在哪块区域，才知道自己究竟在操作什么。

## 与其他语言的对比

不同语言对内存的管理策略差别很大。同样是创建一个存 1000 个数的数组、用完销毁，各语言的做法与代价截然不同。

Python 的内存由解释器全权管理，开发者无需关注分配与释放。

```python
data = [0] * 1000
data = None  # 或直接离开作用域，垃圾回收器会在某个时刻自动回收
```

代价是回收时机不可控，由垃圾回收（GC）策略决定，且无法直接感知内存布局。

Java 与之类似，所有对象都分配在堆上，由 JVM 的垃圾回收器统一管理。

```java
int[] data = new int[1000];
data = null;  // 离开作用域后 GC 自动回收
```

代价是 GC 触发时可能引起 Stop-The-World 暂停，这在对实时性有严格要求的场景（如机器人控制）中不可接受。

C 没有构造函数、析构函数和智能指针，内存的分配与释放完全靠开发者显式控制。

```c
int* data = (int*)malloc(1000 * sizeof(int));  // 手动在堆上分配
// ... 使用 data ...
free(data);  // 手动释放，遗漏则内存泄漏
```

C++ 则把选择权交给开发者，可以栈上分配自动回收，可以堆上分配手动控制，也可以用智能指针实现自动管理。

```cpp
int data_stack[1000];                          // 栈上分配，离开作用域自动释放

int* data_heap = new int[1000];                // 堆上分配 + 手动管理
delete[] data_heap;

auto data_smart = std::make_unique<int[]>(1000);  // 堆上分配 + 智能指针，自动管理
```

C++ 的核心哲学是"不为不使用的特性付出开销"（zero-overhead principle）：需要多大控制权，就承担多大责任。理解内存模型，正是做出正确选择的前提。至此入门篇告一段落，指针与内存这两章打下的底子，会在 C++ 进阶篇里继续发力——移动语义、RAII、智能指针的深入用法，都建立在对栈、堆和地址的这份理解之上。
